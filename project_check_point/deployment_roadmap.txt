1. PROJECT UNDERSTANDING
======================================================================

Problem:
- Kaggle Spaceship Titanic is a supervised binary-classification problem.
- One row represents one passenger.
- The target, Transported, is True/False.
- The model uses passenger details, cabin data, CryoSleep status, destination,
  age, VIP status, and onboard spending to predict Transported.

Current data:
- data/train.csv: 8,693 rows, 14 columns (includes Transported).
- data/test.csv: 4,277 rows, 13 columns (no target).
- There are missing values in both numeric and categorical inputs.

Current implementation:
- notebooks/spaceship-titanic.ipynb contains the learning walkthrough.
- src/pipeline.py performs feature engineering, imputation, one-hot encoding,
  model comparison, holdout evaluation, full-data training, and Kaggle export.
- Compared models: Logistic Regression, Random Forest, and
  HistGradientBoostingClassifier.
- Current best model: HistGradientBoostingClassifier.
- Verified baseline on 2026-10-14:
  * 5-fold CV accuracy: 0.8036 (+/- 0.0093)
  * Holdout accuracy: 0.8079
  * Submission file: submissions/submission.csv

Useful engineered features already present:
- Cabin -> Deck and CabinSide
- PassengerId -> Group
- Group -> GroupSize
- Five spending fields -> TotalSpend

======================================================================
2. IMPORTANT GAPS TO FIX BEFORE DEPLOYMENT
======================================================================

1. Preprocessing leakage
   engineer(), impute(), and get_dummies() currently run before cross-validation
   and the holdout split. Medians, modes, group-derived values, and encoded
   columns can therefore use information outside a training fold. All learned
   preprocessing must be fit only on the training portion of each split.

2. Training/serving mismatch
   GroupSize and group-based HomePlanet/CabinSide imputation are computed from
   the entire input DataFrame. A single-passenger API request would make
   GroupSize equal 1 and would have no group-mates available. Choose and document
   one production policy:
   - Recommended first version: accept a batch of passengers and compute group
     features within that batch, while using safe fitted fallbacks for single
     predictions; or
   - Store a fitted group lookup from training data and use it only when a known
     group is supplied, with safe fallbacks for unseen groups.
   The behavior must be identical during training, testing, API use, and UI use.

3. No saved model artifact
   The program retrains whenever it runs. Production should train separately,
   save one versioned preprocessing+model artifact, and load it for inference.

4. No API or UI
   FastAPI should own prediction logic. Streamlit should be a thin user interface
   that calls the API rather than duplicating the model code.

5. No automated validation
   Add unit, integration, schema, and smoke tests before deployment.

6. Reproducibility and repository hygiene
   Dependencies need production/dev separation or a lock strategy. Add a real
   .gitignore, configuration, logging, and clear commands. Avoid committing raw
   competition data or generated model binaries unless licensing and repository
   size are deliberately handled.

======================================================================
3. TARGET ARCHITECTURE
======================================================================

Browser
  -> Streamlit web app (forms, CSV upload, explanations/results)
  -> FastAPI service (/health, /model-info, /predict, /predict-batch)
  -> validated request schema
  -> saved sklearn preprocessing+model artifact
  -> prediction and optional probability

Training is a separate offline path:
  train.csv -> validation + feature transformer + model -> evaluation report
            -> versioned artifact + metadata

Why separate these paths:
- Training can be slow and should not happen when the server starts.
- One shared artifact guarantees the API applies the same transformations used
  during training.
- Streamlit can change without retraining, and the model/API can be tested and
  scaled independently.
